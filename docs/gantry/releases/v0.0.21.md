# Gantry v0.0.21

Gantry v0.0.21 unifies sandbox launch and readiness behavior across the CLI,
terminal dashboard, and manager API. It adds honest current-versus-next-boot
resource reporting, host-aware dashboard memory controls, and a standalone
product website and searchable manual.

> [!NOTE]
> Gantry remains experimental. Linux and Apple silicon macOS are supported.
> Windows support remains experimental.

## Highlights

### One lifecycle contract

Create and resume now use a typed application service shared by Gantry's CLI,
dashboard, and HTTP adapters. Each frontend converts its own input—CLI flags,
dashboard form state, or HTTP JSON—into the same launch options. Configuration
resolution, the cross-process launch lock, cache policy, readiness, warnings,
and cancellation no longer depend on reconstructing another frontend's input.

The manager no longer rebuilds CLI flag sets for HTTP requests, and the
dashboard no longer launches a child Gantry CLI and scrapes terminal text when
creating a sandbox. The manager retains its cache-only image policy and
read-only root default. The dashboard receives structured progress and warning
events directly while image preparation and persistent-disk creation run in
the background.

Closing the dashboard cancels and joins unfinished launch work. Cancellation
before readiness terminates and reaps the uncommitted daemon, including when a
large inherited handshake would otherwise remain blocked. Once readiness is
published, the persistent sandbox owns the daemon independently of the caller.

### Honest active and desired settings

The common inspection model distinguishes three sandbox states:

- `starting` — the lifetime lock or daemon exists, but both guest RPC and the
  local control broker are not ready yet;
- `running` — the ready contract has been published; and
- `stopped` — no sandbox daemon owns the saved configuration.

The daemon publishes an immutable snapshot of boot settings before readiness.
Manager responses now include:

- `desired` for saved CPU, memory, process-isolation, and Dev Containers
  settings;
- `active` for settings allocated to the running VM; and
- `restartRequired` when saved settings differ from the active boot.

`active` is absent for stopped sandboxes and can be absent for daemons started
by older Gantry versions. Existing top-level `cpus` and `memoryMiB` fields keep
their saved-setting meaning. Lifecycle operation responses also expose
preparation warnings.

The OpenAPI 3.1 contract documents the new state and fields. Contract tests now
compare registered manager routes and JSON models with the schema, while
architecture tests protect the intended dependency direction between
presentation adapters, lifecycle services, inspection, workers, and the core
sandbox implementation.

### Host-aware dashboard resources

The dashboard's create and edit memory sliders now stop at total physical host
memory instead of offering Gantry's 1 TiB architectural ceiling. Gantry detects
the value natively on Linux, macOS, and Windows, rounds it down to MiB, and
keeps it within the VM-wide minimum and maximum. If detection is unavailable,
the dashboard falls back to a conservative 512 MiB limit.

CPU controls continue to use the current host's supported vCPU count. Existing
sandbox allocations above a current host's physical-memory limit no longer
expand the edit slider beyond that safe maximum. Mouse selection can still
reach the exact host maximum even when it is not aligned to the slider's
128 MiB keyboard step.

The New Sandbox form now owns its inputs, request construction, validation
focus, and rendered control geometry as one component. Keyboard navigation,
mouse targets, responsive sections, and inline validation therefore use the
same layout state.

### Product website and standalone manual

The repository now includes a responsive product website and a generated
manual containing every Gantry guide and release note. Both are dependency-free
static HTML pages that embed their styles, icons, and interactions and make no
external asset requests, so they work directly from a checkout and offline.

The manual adds:

- grouped sidebar navigation and a responsive mobile guide menu;
- local full-text search with keyboard navigation;
- deep links, browser history, and an on-page outline;
- highlighted examples with explicit copy controls;
- dark and light themes, print styles, and reduced-motion support; and
- a no-JavaScript mode in which every guide remains readable.

Markdown stays the source of truth. A pinned Python generator validates local
links and heading fragments, preserves the exact text of fenced examples, and
fails rather than introducing a remote runtime image dependency.

A GitHub Pages workflow rebuilds and tests the manual for pull requests and
deploys it from `main`. The Pages artifact contains only the product HTML, the
manual HTML, and a `.nojekyll` marker; repository sources, credentials, VM
images, and local artifacts are not published.

## Reliability and validation

- Dashboard subprocess diagnostics retain only a bounded tail, reject
  oversized progress lines, and can recover on a later valid progress update.
- Create mode rejects an existing saved sandbox before resolving or downloading
  assets, preventing an accidental replacement through another frontend.
- Invalid saved configuration remains visible as inspection data so frontends
  can list and diagnose the sandbox instead of losing it from their view.
- API contract changes now trigger the main CI workflow.
- The Linux KVM port-forward battery uses BusyBox netcat's persistent-listener
  form and retains the final curl diagnostic when a forwarded service fails.
- The complete Go test suite and `go vet ./...` pass. The host-memory service
  also cross-builds for Apple silicon macOS and x86-64 Windows.
- Documentation generator tests cover source discovery, links, escaping,
  release ordering, example fidelity, deterministic output, and GitHub Pages'
  `/gantry/` project prefix. Browser validation covers all guides, search,
  copy fallbacks, themes, deep links, keyboard controls, 320–1440 px layouts,
  accessibility, no-JavaScript reading, and zero external requests.

## Compatibility and operational notes

- Existing sandbox configurations require no migration.
- Manager clients with a closed state enum must accept `starting` in addition
  to `running` and `stopped`.
- Manager clients should use `active` for current VM resources and `desired`
  for saved next-boot settings. They must tolerate a missing `active` object.
- The dashboard's physical-RAM ceiling is a presentation limit. Existing CLI
  resource validation and Gantry's architectural memory maximum are unchanged.
- A repository administrator must select **GitHub Actions** as the Pages source
  once before the new deployment workflow can publish. After that, matching
  pushes to `main` deploy automatically; pull requests are build-only.
- The website is expected at `https://ejpir.github.io/gantry/` and the manual at
  `https://ejpir.github.io/gantry/docs/gantry/` after Pages is enabled and the
  changes reach `main`.
