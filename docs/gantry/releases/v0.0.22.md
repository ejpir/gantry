# Gantry v0.0.22

Gantry v0.0.22 makes browser OAuth work for unmodified tools anywhere inside a
sandbox and gives the terminal dashboard a clearer, more searchable operational
interface. It also refreshes the product website and strengthens native and
field validation around helper delivery and port forwarding.

> [!NOTE]
> Gantry remains experimental. Linux and Apple silicon macOS are supported.
> Windows support remains experimental.

## Highlights

### Automatic guest OAuth listener discovery

The default OAuth callback bridge no longer depends on recognizing a login URL
in terminal output. A daemon-owned trusted helper now watches the guest network
namespace for new loopback TCP listeners and reports bounded snapshots to the
host. This works for unmodified CLIs launched directly, nested under coding
agents, or running inside terminal multiplexers.

Gantry mirrors eligible listeners on host loopback and replays OAuth callbacks
into the guest. The supported set includes the fixed callback ports used by
Codex and Pi and Linux's normal ephemeral-port range, including root callbacks
such as `http://localhost:<port>`.

Discovery starts before sandbox readiness is published, so a login launched
immediately after `gantry start` cannot race the watcher. Existing listeners are
treated as a baseline instead of being exposed automatically, newly opened
listeners create host gates, and a host gate closes when its guest listener
disappears. Watcher shutdown closes all transparently discovered gates.

The bridge remains an OAuth-specific gate rather than a general-purpose port
forward:

- host listeners bind only to `127.0.0.1`;
- transparent callbacks must be GET requests containing non-empty `state` and
  either `code` or `error`;
- only the path and query are replayed—browser headers and cookies do not cross
  into the guest;
- the guest CLI remains authoritative for OAuth state and PKCE validation;
- listener count, snapshot size, callback size, replay concurrency, and replay
  duration are bounded; and
- the browser receives only Gantry's fixed, CSP-locked completion page, never a
  guest-controlled status, redirect, header, or response body.

OAuth custody retains its stricter exact pending-state check and independent
listener lifecycle.

### A redesigned operational dashboard

The terminal dashboard now shares the product site's neutral green visual
language, with coordinated dark and light palettes, a responsive Gantry
wordmark, clearer surface hierarchy, and consistent semantic colors for
running, warning, and error states.

The Overview uses larger operational cards with explicit state, resources,
traffic totals, blocked packets, access, mounts, and recent denied hosts. Wide
terminals add a selected-sandbox inspector with mount, network-policy,
published-port, recent-block, and action summaries. Narrow terminals preserve
the same information in a compact stacked layout.

The Sandboxes detail pane now renders the actual runtime topology as a
responsive stack:

```text
workload and optional development environment
                    inside one microVM
                           │
                Gantry supervisor + workers
                           │
                    native host hypervisor
```

The diagram distinguishes the workload image and writable storage from the
optional curated Dev Containers environment. It adapts through full, icon, and
compact modes, and its rendered action geometry is also used for mouse hit
testing so resized or clipped layouts remain accurate.

### Filtering, sorting, and discoverable controls

Press `/` to filter every sandbox-scoped view by a case-insensitive substring
of the sandbox name. The filter applies consistently to sandboxes, traffic,
rules, mounts, ports, secrets, MCP servers, and packets; Images and registry
credentials remain host-wide. Clearing the filter restores rows from the
latest source snapshot without waiting for another refresh.

Tables can now be sorted by clicking a visible column heading. Click the same
heading again to reverse direction, or press `S` to select any available field,
including fields hidden by a narrow terminal. Sort state is remembered per view
for the dashboard session, and refreshes, filters, and sorting retain the
selected record whenever it remains visible.

The `?` dialog has been reorganized into aligned Navigation, current-view
Actions, Filter & Sort, and Application sections. It reflows into two columns
on wide terminals and a scrollable single column on smaller screens, making
mouse and keyboard controls discoverable without crowding the status bar.

### Refined product website

The standalone product page now offers a light theme aligned with the manual,
while code and terminal examples retain a consistent dark surface. Theme
selection is stored locally and shared with the documentation site when both
are served from the same origin.

The landing page also uses clearer feature descriptions and runnable workflow
examples, improves no-JavaScript presentation, tightens responsive navigation,
and simplifies platform, architecture, and installation guidance. It remains a
single dependency-free HTML file with no telemetry or external runtime assets.

## Reliability and validation

- Guest listener snapshots are size- and count-bounded; malformed or oversized
  reports are discarded without blocking the helper stream.
- OAuth watcher startup requires an initial guest snapshot before daemon
  readiness and fails closed if the helper exits or does not initialize in
  time.
- Guest-tool staging on Windows uses a private secured sibling of Gantry's
  protected state root, avoiding both state-tree overlap and service-inaccessible
  temporary directories.
- Dashboard tests cover responsive overview and topology layouts, dark and
  light contrast, filter projection, per-view sorting, selection retention,
  clickable headings, dialog scrolling, and help rendering.
- OAuth tests cover procfs listener parsing, watcher lifecycle, malformed
  snapshots, listener bounds, callback validation, replay limits, and
  guest-response isolation.
- The Linux KVM port-forward fixture now waits for a complete in-guest HTTP
  round trip before evaluating host forwarding and preserves the final curl
  diagnostic on failure.
- The offline read-only native smoke test explicitly disables OAuth bridging,
  keeping the test focused on boot and exec without downloading or delivering
  the optional guest helper.

## Compatibility and operational notes

- Existing sandbox configurations require no migration.
- OAuth bridging remains enabled by default. It now requires the trusted
  `gantry-guest` helper, which may be downloaded and integrity-verified on first
  use. Disable it with `-oauth-bridge=false` for fully offline sandboxes or when
  browser login is not needed.
- The automatic bridge recognizes callback listeners on ports `1455`, `53692`,
  and `32768–65535`. Use explicit port publishing for ordinary services; the
  OAuth gate intentionally rejects non-OAuth requests.
- Dashboard filtering and sorting are presentation-only. They do not alter
  network policy, packet-capture scope, retained traffic, or sandbox state.
- Dashboard sort and filter preferences last for the current TUI session and
  are not persisted to sandbox configuration.
