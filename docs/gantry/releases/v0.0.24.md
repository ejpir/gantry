# Gantry v0.0.24

Gantry v0.0.24 adds a native desktop client preview, declarative sandbox
manifests, and full dashboard parity for remote managers. Shared-folder
metadata on macOS is now cached end to end, measurably speeding up compile
workloads, and split-VMM confinement now boots on stock Ubuntu 24.04+ and on
macOS 15 running on M4 hardware.

> [!NOTE]
> Gantry remains experimental. Linux and Apple silicon macOS are supported.
> Windows support remains experimental.

## Highlights

### Native desktop preview

The new `desktop/` crate is a native Rust/GPUI client for the manager API,
shipped as preview binaries for Linux (x86-64), macOS (Apple silicon), and
Windows (x86-64) on the release page. It uses the same authenticated
transports as the CLI: a local Unix socket with an on-demand manager start, or
a remote HTTPS profile. Closing the window never stops the manager or any
sandbox.

The workspace follows the approved design study: a unified toolbar, a source
sidebar for local and remote connections, and a resizable inspector.
Right-click (or **…**) acts on the exact sandbox row, re-checking connection
and state before any write form opens. Create and Settings forms offer CPU and
memory sliders with exact numeric entry, bounded by the selected manager's
limits; **Browse…** opens the native file and folder chooser for paths that
live on the selected manager's host. Activity keeps a bounded, in-memory log
of this window's submissions with UTC timestamps. Demo mode is strictly
read-only.

This is a working preview, not yet full TUI parity: it selects one host at a
time, and interactive terminals, organization login and catalog flows, live
SSE updates, and persistent preferences remain follow-up work.

### Declarative sandbox manifests

Gantry now accepts strict, versioned YAML manifests for repeatable sandbox
creation:

```sh
gantry manifest validate gantry.yaml
gantry apply --check -f gantry.yaml
gantry apply -f gantry.yaml
```

A manifest declares the image, CPU/memory/disk resources, root writability,
shares, network ports, secrets, and SSH. `apply --check` previews the
transition; `apply` reconciles toward the declared state. Applied manifests
record provenance (API version and digest) so a later apply can detect
imperative drift — any CLI mutation of covered settings clears the recorded
provenance instead of silently diverging. The saved `sandbox.json` remains
internal resolved state and must not be edited.

### Full remote dashboard parity

The manager API gained a host dashboard snapshot endpoint (snapshot, resource
limits, and kernel choices) plus dashboard action and packet-capture routes.
The terminal dashboard and the desktop client reach the same telemetry,
configuration, and capture surface for remote managers as for the local one,
keeping local and remote sources explicitly scoped.

### Faster shared folders on macOS

The virtio-fs share hub served its synthetic namespace (hub root, export
entries, and export roots) with a zero cache TTL, so every guest path walk
revalidated the namespace with LOOKUP/GETATTR round trips. On an M4 build of
a Go CLI this produced ~180k metadata requests out of ~275k per build and
cost roughly 15–30% elapsed time.

Namespace changes already push dentry invalidations over the reverse
notification virtqueue, so once that channel is live the zero TTL is
unnecessary: namespace roots are now cached with the watched TTL exactly when
notifications are ready, keep TTL 0 otherwise, and negative entries are never
cached. Measured on the same build: ~275k → ~110k requests and 184s → 157s
warm elapsed time.

### Confinement compatibility

- **Ubuntu 24.04+ (AppArmor user-namespace restriction):** the split-VMM
  worker sizes its inherited kernel, initrd, and disk descriptors with
  `lseek` when `fstat` is denied, instead of failing the boot with
  `stat kernel: permission denied`. The AppArmor-generated profile attached
  on unprivileged user-namespace creation mediates path-based metadata
  operations on inherited descriptors but not reads or seeks; `auto` mode no
  longer silently falls back to a monolithic VMM on stock Ubuntu, and
  `required` mode boots.
- **macOS 15 on M4:** the VMM worker Seatbelt profile now permits reading
  `hw.pagesize_compat`, which `hv_gic_create` requires; its denial surfaced
  as an unhelpful `HV_BAD_ARGUMENT`.

## Reliability and validation

- Share filesystem internals were reorganized around explicit ownership:
  export state owners, serialized prepared-share handover, joined watcher
  shutdown, FUSE handles released before share roots, and Windows share-handle
  teardown moved into the owning layer.
- VMM boot assets are fully prepared before path confinement is applied, and
  the Windows VMM worker confinement build regression is fixed.
- Sandbox, dashboard, and manager state moved into owning subpackages; the
  changes are internal and do not alter CLI behavior.
- New diagnostic knobs for the macOS hypervisor and share paths
  (`GANTRY_HVF_STATS`, `GANTRY_VHOST_STATS_EVERY`, `GANTRY_VHOST_TRACE`),
  documented in the troubleshooting guide; all are off by default.
- CI lints every target (`linux/amd64`, `linux/arm64`, `darwin/arm64`,
  `windows/amd64`) and runs the full local KVM battery on Linux, including
  the SSH/Dev Containers, large-directory, and policy suites.
- Desktop binaries build natively on Linux, macOS, and Windows runners from
  the locked crate manifest, with the headless test suite gating Linux.
- Timing-sensitive policy and configuration-transaction tests were hardened
  for heavily loaded CI runners without relaxing the production fail-closed
  budgets they assert.

## Compatibility and operational notes

- The desktop client is a preview: one host at a time, no interactive
  terminals or organization flows yet, and demo mode never permits writes.
  Release archives contain the bare binary; desktop binaries are not yet
  notarized or Authenticode-signed.
- Manifest provenance is cleared by any imperative mutation of covered
  settings; re-apply the manifest to re-establish drift detection.
- Share-namespace caching engages only when the reverse notification channel
  is live; without it, behavior is unchanged (TTL 0, hot-add immediately
  visible). Negative lookups are never cached.
- Existing sandboxes, remotes, and policies require no migration.
