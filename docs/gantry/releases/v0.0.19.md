# Gantry v0.0.19

Gantry v0.0.19 adds first-class SSH access and VS Code Dev Containers while
preserving Gantry's single-microVM architecture and workload isolation model.
It also includes startup, session, filesystem, networking, self-update, and
Windows reliability improvements.

## Highlights

### SSH and editor access

Persistent sandboxes can now expose an SSH environment without opening an
inbound network port:

```sh
gantry start dev -image ubuntu:latest -ssh
gantry ssh doctor dev
gantry ssh dev
```

Run `gantry ssh setup` to use regular OpenSSH clients with managed `*.gantry`
hostnames. This supports VS Code Remote SSH, command execution, SFTP, SCP,
rsync, and local port forwarding.

SSH setup is delivered asynchronously, so `start`, `resume`, and the dashboard
do not wait for editor tooling. An SSH connection made immediately after boot
waits for setup to finish rather than failing.

### Dev Containers inside Gantry

Enable the curated development environment with:

```sh
gantry start dev -image ubuntu:latest -ssh -devcontainers
```

The VS Code Dev Containers extension reads the project's
`.devcontainer/devcontainer.json` and uses the curated environment's
Docker-compatible CLI to build and start the inner container with Podman.
Nested images and volumes persist across stop/resume.

The SSH/editor session remains the unprivileged `gantry` user. The bundled
`podman` and `docker` commands transparently invoke rootful Podman through a
narrow passwordless `sudo` launcher, avoiding the nested user-namespace
limitations of rootless Podman.

### One VM, separate workload and IDE environments

Dev Containers do not replace the image selected by `-image`. Gantry runs two
peer `crun` environments in the same microVM:

```text
microVM
├── workload container selected by -image
└── curated IDE container
    └── nested Podman Dev Container
```

`gantry exec` continues to enter the workload container, while SSH and Dev
Containers use the curated IDE environment. Each has an independent read-only
image and private writable layer. `gantry export` exports only the workload;
the IDE layer and host shares are excluded.

### Reliability and platform improvements

- Preserves nested Podman images and volumes while clearing stale runtime state
  after a VM reboot.
- Stabilizes concurrent session setup and split-VMM stream pairing.
- Extends the split VMM descriptor table to carry both workload and IDE
  writable disks directly, avoiding block-proxy overhead.
- Recovers from transient Hypervisor.framework `UNKNOWN` exits with bounded
  retries and emits full vCPU diagnostics if the condition persists.
- Improves virtio-fs notifications and spreads virtio interrupts across vCPUs.
- Makes guest-tool delivery, self-update metadata handling, and persistent
  session setup more resilient.
- Bounds writable-layer export work so guest-created sparse files cannot cause
  unbounded host CPU, I/O, or archive growth.
- Restricts runsc hang diagnostics to the supervised runtime process so one
  session cannot signal unrelated gVisor workloads in the same microVM.
- Hardens Windows worker startup, socket relay, environment inheritance, and
  temporary-path handling. Windows support remains experimental.
- Preserves remote SSH command argument boundaries consistently on Linux,
  macOS, and Windows.

## Operational notes

- `-devcontainers` requires `-ssh` and the default `crun` runtime.
- Enabling or disabling Dev Containers on an existing sandbox requires a
  restart because the IDE image and writable disk are part of the VM's boot
  device topology.
- Unless overridden, the Dev Containers profile uses 4096 MiB of memory, four
  vCPUs (capped by the host), and a 32768 MiB IDE writable disk.
- Running inner containers do not survive a VM restart, but their images,
  volumes, and filesystem data do.
- Dev Containers are Linux containers inside the Linux microVM on every host
  platform, including Windows.
