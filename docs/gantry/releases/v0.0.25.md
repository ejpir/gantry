# Gantry v0.0.25

Gantry v0.0.25 adds an organization policy service, a native desktop workspace
for administering it, and managed enrollment of existing remote managers.
Administrators can publish signed policy in rollout rings and inspect what each
host reports; host owners can stage and activate a feed without handing the
service a signing key, manager token, or host private key. The desktop also
adds an embedded browser for local sandboxes.

> [!NOTE]
> Gantry remains experimental. Linux and Apple silicon macOS are supported.
> Windows support remains experimental.

## Highlights

### Organization policy service

`gantry policy-service` is a self-hosted distribution point for one
organization's signed policy. Enrolled managers long-poll it over mutual TLS;
administrators use a separate bearer-authenticated API. The service verifies
policy but never receives the organization's signing key.

A service keeps a draft, immutable generation history, host enrollment and
revocation state, and ordered rollout rings (by default `canary`, `early`, and
`everyone`). Publishing verifies that the signed bundle matches the pinned
organization and public key and covers every enrolled profile. Administrators
can then promote the generation ring by ring. Rolling back republishes an older
signed bundle under a new generation number without extending its expiry.

Managers now report their offered, pending, applied, stalled, rejected, or
mismatched generation on every poll. A generation that cannot reach every
sandbox remains pending and keeps retrying instead of being acknowledged or
silently disappearing.

Create a stable signing key and initialize a service with the new commands:

```sh
gantry policy keygen -out ~/secure/acme-key
gantry policy-service init -dir /srv/acme-policy -organization acme \
  -url https://policy.acme.dev:8443 -public-key ~/secure/acme-key/public.pem
gantry policy-service admin add -dir /srv/acme-policy -name ops-admin
gantry policy-service serve -dir /srv/acme-policy
```

Keep the signing key on an administrator's machine. `admin add` prints its
administrator token only once.

### Native policy administration

Register a policy service as an ordinary remote profile and Gantry desktop
recognizes its `policy-service-admin-v1` capability. It opens an organization
workspace with five views:

- **Hosts** shows enrolled managers by ring and their reported rollout state.
- **Policy** edits the next draft and classifies rule-level changes as
  tightening or loosening access.
- **Rollouts** promotes the current generation and charts acknowledgements.
- **History** inspects generations and republishes an earlier bundle.
- **Enrollment** enrolls, activates, and revokes hosts.

**Sign & Publish** saves the draft, invokes the local Gantry CLI to sign it,
checks that the key matches what hosts pin, and uploads only the signed bundle.
The private signing key is never sent to the service.

### One-click managed-host activation

**Enroll managed remote…** connects separately to an existing remote manager
and the policy service. The manager creates its private key on its own host and
exports only a stable certificate request. Desktop returns the signed
certificate and public trust files, validates their identity and pins, and
stages `feed.json`. Enrollment is deliberately labeled **not enforcing**.

After a signed generation is available for the host's ring, **Activate feed…**
fetches and verifies it, applies it to every saved sandbox, and attaches the
live receiver without attempting to restart the manager. An unreachable
service or empty ring leaves the enrollment staged. A partial rollout remains
pending under mandatory admission; failed targets are subject to a fail-closed
stop and continue to retry. Successful activation records the applied
generation and restores the same pinned feed on later manager starts using the
manager's existing listener and authentication flags.

The policy-service administrator token and manager bearer token remain
separate. Neither API exports the host private key. The feed URL must be
reachable from the manager host; a desktop-to-manager SSH forward does not
provide manager-to-service connectivity.

### Embedded browser for local sandboxes

A running local sandbox now has a **Browser** tab. **Open Browser** starts
Chromium inside the microVM and streams its page through Chrome DevTools
Protocol over `gantry exec`. No browser port is published and no debug service
listens on the network. Navigation, clicks, scrolling, typing, clipboard
operations, and pane-size changes are forwarded to the guest browser, whose
traffic remains subject to the sandbox's network policy.

The guest image must provide Chromium. This preview is local-manager only and
does not yet support pop-up windows, audio, or HiDPI rendering. Chromium's own
sandbox is disabled; the Gantry microVM remains the security boundary.

## Reliability and validation

- Managed enrollment uses stable CSR retries, validates organization, host,
  profile, feed URL, CA, and signing-key pins, and writes host identity with
  platform-native private permissions. Windows tests inspect the key's DACL
  rather than Unix mode bits.
- Activation is authenticated separately from staging, refuses success until a
  signed generation can be applied, joins its receiver during shutdown, and
  persists only a validated activated identity for restart restoration.
- The real-process manager API battery covers enrollment authentication, CSR
  reuse, altered-trust rejection, guarded restart, pre-publication activation
  refusal, and pinned-feed startup. Local Linux E2E builds the Gantry binary
  from the checkout by default instead of accidentally testing a stale
  artifact.
- Policy-service tests cover mTLS host identity, administrator-token rotation,
  signed publication, ring promotion, republished rollback, host revocation,
  long polling, durable state, and rollout reporting. Desktop integration tests
  exercise the real service and manager.
- Denied UDP DNS names under a default-deny network policy now receive an
  immediate `REFUSED` response without reaching the upstream resolver, rather
  than making the guest wait for a timeout. Domain lists under a default-allow
  local policy remain allowances; organization DNS restrictions still apply.
- The macOS E2E HTTP fixture now drains request headers before replying, avoiding
  reset-truncated response bodies, and host-permission fixtures no longer alter
  the runner's real SSH directory.

## Compatibility and operational notes

- Existing ungoverned managers and sandboxes require no migration. Enrollment
  is opt-in and staging alone does not enforce organization policy.
- A staged but inactive managed enrollment still blocks automatic ungoverned
  manager startup. Activate after publishing a signed generation, or restart
  explicitly with the displayed `-policy-feed` path. A successfully activated
  feed is restored automatically on subsequent starts.
- The policy service must be reachable from every enrolled manager at its
  stable TLS URL. Protect administrator tokens like manager tokens and keep
  the signing key off the service.
- Feed policy remains manager-wide: it governs all saved and future sandboxes,
  prevents per-sandbox policy replacement, and disables unmanaged low-level
  runs after activation.
- The embedded browser requires Chromium in the guest and currently supports
  only a local manager. Remote integrated terminals remain available as before.
