# Gantry v0.0.23

Gantry v0.0.23 adds signed organization policy, optional OIDC organization
login, and authenticated remote sandbox management. It also expands host-side
OAuth custody for coding tools and MCP servers, and adds the same workflows to
the terminal dashboard and manager API.

> [!NOTE]
> Gantry remains experimental. Linux and Apple silicon macOS are supported.
> Windows support remains experimental.

## Highlights

### Signed organization policy and audit

A sandbox can now pin a signed organization policy at creation or apply it
live. Policy profiles govern:

- network destinations, protocols, ports, and DNS;
- readable and writable host directories;
- MCP server connections, tool discovery, and tool calls; and
- release of brokered credentials to approved hosts.

Organization rules are an additional restriction. They cannot relax Gantry's
built-in checks or the sandbox's local network policy. Deny wins, and missing,
invalid, expired, or unevaluable policy denies governed access. Policy expiry
also initiates sandbox shutdown.

Use a supplied bundle and public key directly:

```sh
gantry start dev -image alpine:latest \
  -org-policy bundle.tar.gz -org-policy-key public.pem \
  -policy-profile developer
```

The new `gantry policy` commands can generate a local test policy, sign policy
data, verify or evaluate a bundle offline, and set, show, or clear a sandbox
snapshot. Bundles are data-only and RSA-signed; Gantry embeds the
authorization logic rather than accepting executable Rego from a bundle.

A long-running manager can now receive new generations of signed policy from
one outbound mTLS policy feed. It locally pins the organization, manager-wide
profile, verification key, and client identity. Monotonic generation state
rejects replay and changed content. Each generation fans out to all running and
stopped sandboxes, and later manager-created sandboxes inherit it. Running
sandboxes update network, share, MCP, credential, persistence, and expiry
enforcement live; a failed target is stopped and prevents aggregate
acknowledgement. The manager API and remote CLI retain an explicit controlled
restart option for manual per-sandbox policy.

Authorization decisions are available through `gantry audit`, the dashboard's
**Audit** view, and the manager API. Audit records include the decision,
matching rule IDs, organization, revision, profile, and action, but omit tokens,
MCP arguments and results, and resource contents.

### OIDC login and trusted remote discovery

`gantry org login` performs host-side OIDC Authorization Code login with PKCE.
A trusted organization configuration maps exact identity-provider group claims
to profiles in a signed policy bundle. Gantry validates the identity and saves
only a token-free, expiring receipt; ID, access, and refresh tokens are not
persisted or delivered to a guest.

```sh
gantry org login -config organization.json
gantry org status example-company
gantry org apply example-company dev
gantry org logout example-company
```

Login is optional and never changes an existing sandbox automatically.
`org apply` applies the verified snapshot live to a running sandbox or saves it
for a stopped sandbox.

An organization configuration may also name a dedicated HTTPS remote catalog.
After validating identity and membership, Gantry can retrieve an expiring list
of approved manager endpoints and TLS trust metadata:

```sh
gantry org remotes example-company
```

Discovery supplies suggestions, not access. It never installs a profile,
changes a default target, or provides the separate manager bearer token.

### Authenticated remote sandboxes

`gantry serve` can now expose the manager API through a TLS listener protected
by a bearer token. Plaintext network listeners and disabled TLS verification
are refused. Managers can use an existing certificate or Gantry's self-signed
local CA mode.

Client profiles keep public endpoint and TLS metadata separate from their
owner-only token files:

```sh
gantry remote add team https://gantry.example.com:8443 --ca manager-ca.pem
gantry remote test team
gantry image pull alpine:latest -remote team
gantry start dev -image alpine:latest -remote team
gantry exec dev -remote team -- uname -a
```

Remote dispatch is available for sandbox lifecycle, images, bounded exec and
low-level run, SSH, events, network policy, organization policy, and audit.
Failures never fall back to a local operation. Remote SSH upgrades an
authenticated manager request into a tunnel to the selected sandbox and pins
the learned host key per profile.

The dashboard keeps local and remote inventories source-scoped while showing
both in **Overview** and **Sandboxes** with explicit remote profile tags. Its
create flow offers explicit **Local**, **Remote**, and **Organization** paths,
while the **Remotes** view can add, test, and remove profiles or refresh
organization discovery. Credentials are masked, write-only, and cleared when
onboarding finishes or is cancelled.

### Provider-scoped OAuth custody

Host-side OAuth custody now supports configured public OAuth clients in
addition to built-in providers. Authorization-code and device-code grants can
deliver current access through an approved guest auth file, an exact
credential-helper hostname, or host-side MCP injection. GitHub device login can
serve Git-over-HTTPS without creating a guest `GITHUB_TOKEN` or `gh` auth file.

Refresh tokens remain in protected host state and survive stop and resume.
Only configured adapters receive access tokens; built-in guest auth files use a
nonfunctional refresh-token sentinel. Refresh rotation is atomic, and replacing
a refresh scheduler now cancels and joins the previous generation so two loops
cannot submit the same rotating token.

The transparent guest OAuth callback bridge also accepts bounded URL-encoded
`response_mode=form_post` callbacks. Duplicate result fields, mixed query/form
results, oversized bodies, unexpected content types, and guest-controlled
browser responses remain rejected.

## Reliability and validation

- Remote token files use owner-only Unix permissions or protected Windows ACLs;
  permissive files are rejected before use.
- Windows onboarding tests now validate token security through the platform ACL
  implementation instead of assuming Unix mode-bit behavior.
- Windows release binaries are published directly from the reproducible build;
  Authenticode signing is temporarily disabled.
- Organization network policy is compiled into a validated native packet guard;
  tests compare it with the policy decision and retain packet-bypass cases.
- Policy-feed tests cover mTLS client authentication, pinned signing trust,
  durable generation and bundle recovery, replay refusal, aggregate fan-out,
  inheritance by later creates, fail-closed target handling, and live
  application without PID changes.
- Daemon-owned guest-tool installation uses a private bytes-only ephemeral share
  and does not require an organization mount grant.
- Flattened images include runtime bind targets for `/etc/hosts` and
  `/etc/resolv.conf`, including explicitly read-only EROFS roots.
- AWS field validation covers Linux amd64, Linux arm64, and Windows WHPX,
  including live policy feeds, signed policy, SSH/Dev Containers, and large
  directories on both Linux architectures.
- End-to-end coverage now exercises policy enforcement in a real guest, remote
  lifecycle and SSH, OIDC login on Linux, macOS, and Windows, and remote
  dashboard onboarding. Every non-VM battery, including race and virtqueue
  fuzz coverage, runs on Linux, macOS, and Windows; Windows TUI coverage uses
  native ConPTY. Linux CI additionally runs the full manager/policy-feed and
  public-client OAuth/MCP batteries on its native KVM runner.
- OAuth tests use a disposable protocol-level local authorization server to
  cover generic code and device providers, an explicitly configured loopback
  callback, S256 PKCE and single-use code validation, MCP/resource bindings,
  refresh persistence and rotation, and bounded `form_post` replay.
- The manual has shorter task-focused guides for organization login, policy,
  remote access, and OAuth, with implementation details centralized in the
  architecture guide.

## Compatibility and operational notes

- Existing local and ungoverned sandboxes require no migration.
- Organization policy and guest/tool OAuth custody cannot currently be enabled
  on the same sandbox.
- Policy `set`, `clear`, `org apply`, and authenticated manager requests apply
  live to their selected running sandbox. An mTLS feed applies manager-wide and
  prevents per-sandbox replacement or unmanaged low-level runs after its first
  generation. `policy set/clear --restart` or `restart: true` explicitly
  selects controlled stop/update/resume when no feed controls the policy. A
  source bundle changing on disk does not update an already pinned snapshot.
- Live organization-policy changes close active MCP sessions; clients may
  reconnect under the new generation. Newly denied shares remain configured
  but inaccessible until a later policy permits them.
- Organization login has no background refresh. Policy feeds use a separate
  provisioned mTLS identity; logout or receipt expiry does not disable them or
  remove policy already applied to a sandbox.
- A remote manager token grants host-shell-equivalent authority and is not a
  scoped multi-tenant or organization credential. Keep the listener on a
  trusted network and protect the token like a private key.
- Remote CLI creation is cache-only; pull the image on the manager first. Most
  path flags refer to paths on the manager host, while documented upload APIs
  send network policy or signed organization-policy bytes from the client.
- Remote exec is bounded and non-interactive. Use remote SSH for an interactive
  terminal, file transfer, and editor integration.
- Organization OIDC login and catalog discovery require the browser and CLI to
  run on the same host because the callback listener is loopback-only.
